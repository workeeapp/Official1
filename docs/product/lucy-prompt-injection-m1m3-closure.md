## 0. Signal taxonomy

| Class | Meaning | Gate allow? |
|-------|---------|-------------|
| **A. ACL** | May touch resource | Always (≠ intent) |
| **G. Server-grounded** | Injected fact (OPEN_JOBS id, presented invite id, dump line) | **Never alone** |
| **V. Server-verified user action** | Opaque inbound equals server-held command for an **offered** pending (§2) | **Yes** for high-risk |
| **C. Heuristic** | Lexicon / name in text | **Never** |

**Not V:** free-text «כן»; model `collab_invite` / `jobs.answer`; model-written button commands; Explicit Join alone (§6).

## 1. Gate placement

```text
parseReplyMetadata → resolveSpokenMetadata → stripShowTurnMutates
→ dump / intent guards
→ ★ PendingConfirm ingest (Class V → claim + durable execute) ★
→ ★ HighRiskActionGate (strip; may stage pending + offer) ★
→ CORE plan/apply (post-Gate metadata only)
→ relays / delivers / notices / recovery remove
```

High-risk from **model ACTION** must not apply/deliver until Gate strip or staged V execute. Secondary notifies only after primary mutate allowed.

## 2. Class V provenance (creation → offer → consume)

### 2.1 How a V command is born (server-only)

1. Gate strips a high-risk slice from model ACTION and builds an **immutable snapshot** (server-authored).  
2. Server creates `PendingHighRiskConfirm` with:
   - `id`, `userId`, `speakerEmployeeId`, `recipientPhone`, `conversationId`
   - `actionKind`, **snapshot**, **summaryText** + `summaryHash` (hash of canonical summary/snapshot)
   - `confirmCommand` / `cancelCommand` = **cryptographically unguessable** opaque strings generated by the server (never copied from model output; strip any model buttons that collide)
   - `status: pending_offer` (not yet shown)
3. Engine renders summary **from snapshot** and sends the confirm bubble (WA interactive + Lucy thread) with **only** those server commands as button ids.  
4. On successful local persist of the offer message, store `offerChatMessageId`. When Graph returns a wamid, store `offerWamid` durably on the pending row (not only in `whatsapp-outbound-memory`).  
5. Only then promote status to **`offered`**. If offer send fails → `failed_pre_effect` / leave non-offered; **commands must not be consumable**.

**Model text is never verification.** The LLM may describe the offer in `responses`, but authorization buttons and commands are engine-injected from the pending row.

### 2.2 What inbound must match to count as V

All required:

| Check | Rule |
|-------|------|
| Command | `button_reply.id` (or inbound body) **byte-equal** to `confirmCommand` or `cancelCommand` on one row |
| Audience | Inbound WhatsApp `from` matches `recipientPhone`; actor/user match |
| Status | `offered` only (not `pending_offer`, consumed, cancelled, expired, superseded, failed_*) |
| TTL | `expiresAt` not passed |
| Offer binding | Row has `offerChatMessageId` and/or `offerWamid` proving the summary was issued to this user in this conversation |
| Optional context | If Meta provides `context.id` on the tap, it **must** equal `offerWamid` when `offerWamid` is set; mismatch → deny |
| Snapshot integrity | Re-hash / compare stored snapshot+summary before execute |

### 2.3 What must not authorize

| Case | Spec |
|------|------|
| Old button after supersede/expire/cancel/consume | Deny; no side effect |
| Offer message replaced / new plan staged | Prior row → `superseded`; old commands dead |
| Command typed/leaked in another chat or to another phone | Phone/conversation/user bind fails |
| Model emits the same-looking command string in ACTION/buttons | Ignored unless ingest matched **server row** in `offered` |
| Free-text «כן» / paraphrase of summary | Not V |
| Snapshot never offered (`pending_offer`) | Not consumable |

### 2.4 Binding recap (security)

User + employee + WhatsApp + conversation + action kind + immutable snapshot + opaque commands + offered-message proof + one-shot CAS consume. Plan change → new pending + new commands + new summary; never mutate snapshot in place.

## 3. Atomicity vs external effects (no assumed outbox)

### 3.1 Fact from code

- A DB transaction **does not** atomic-commit with Meta WhatsApp (or other external IO).  
- Today there is **no** durable outbound outbox table; `rememberWhatsAppOutbound` is process memory.  
- `reminder-fire` already documents: Graph accept then crash before durable `sendStatus` write ⇒ **at-least-once resend** on next tick.

**Do not implement “assume outbox exists.”** M1–M3 must add an explicit durable delivery ledger for high-risk executes (and reuse the same pattern where schedule fire already needs it).

### 3.2 Durable execution (fits existing stack)

Introduce a small **DeliveryAttempt** (name flexible) row per external side effect in a confirm snapshot (and for foreign schedule fires under P-Out):

| Field | Role |
|-------|------|
| `id` / `confirmId` / `stepKey` | Idempotency key: `confirmId + destination + purpose` (purpose e.g. `relay`, `phone`, `asker_notice`) |
| `status` | `queued` → `sending` → `accepted` \| `failed` \| `unknown` |
| `providerMessageId` | WhatsApp wamid when Graph returns one |
| `lastError` | Optional |

**Protocol:**

1. **Claim confirm** (`offered` → `consuming`) in DB.  
2. Apply **DB-side** snapshot parts in transactions as CORE already allows.  
3. For each external send:  
   - Insert/CAS step `queued` → `sending` (unique on idempotency key). If row already `accepted` → **skip send**. If `sending`/`unknown` → **do not auto-send again** (§4).  
   - Call Graph.  
   - On HTTP OK + wamid → durable `accepted` + store wamid **before** considering the step done.  
   - On clear HTTP/API failure → `failed`.  
   - If process may have sent but status not durable → leave/mark **`unknown`** (crash window).  
4. Finalize confirm status from step outcomes (§4).

**Retry policy:** Automatic retry **only** for steps in `queued` never started, or `failed` with explicit safe policy. **Never** auto-retry `accepted` or `unknown`.

This mirrors the intent of reminder `sendStatus=accepted`, but closes the “wamid only in memory” gap for PendingConfirm paths.

## 4. Failure states & lifecycle

### 4.1 Distinguish three failure classes

| Class | Meaning | Auto retry send? |
|-------|---------|------------------|
| **Pre-effect failure** | Claim/ACL/availability/offer failed; **no** external send started | No send; user may get a new confirm later |
| **Partial failure** | Some DB steps and/or some destinations `accepted`, others `failed` clearly | No full-snapshot replay; **new** confirm only for **remainder** |
| **Unknown external outcome** | Crash/timeout after send may have been accepted; step=`unknown` | **No automatic resend.** Reconciliation or explicit user-driven recovery only |

### 4.2 Lifecycle statuses (pending + delivery)

**PendingHighRiskConfirm:**  
`pending_offer` → `offered` → `consuming` →  
`consumed` | `consumed_partial` | `cancelled` | `expired` | `superseded` | `failed_pre_effect` | `failed_partial` | `needs_reconciliation`

**DeliveryAttempt:** `queued` | `sending` | `accepted` | `failed` | `unknown`

### 4.3 Reconciliation (unknown)

| Action | Spec |
|--------|------|
| Default | Leave `needs_reconciliation`; **do not** call Graph again for that stepKey |
| If status webhooks / durable wamid later prove delivered | Mark `accepted`; close reconciliation |
| If proven not delivered | Mark `failed`; allow **new** confirm for remainder only |
| If still unknown | Operator/user-visible: “לא וידאתי שההודעה נשלמה — לא אשלח שוב אוטומטית”; optional explicit “שלח שוב” creates **new** confirm/snapshot (new idempotency keys), never replays the unknown key |

### 4.4 User reporting

| Outcome | User-facing |
|---------|-------------|
| `consumed` | Exact success matching summary |
| `consumed_partial` / `failed_partial` | What succeeded vs what did not (by destination/op) |
| `failed_pre_effect` | Nothing done; ask to retry / re-stage |
| `needs_reconciliation` | Honest uncertainty; no claim of full success; no silent second send |
| Cancel / expire / supersede | Nothing done for that id |

### 5.2 O11 — explicit verdict

**Path:** `continueInviteAfterRegister` (chat.service) after guest `register` success.

**Effects today:** consume message-invite (no collab payload) → `createJobsFromRelays` for guest → WA ask text to **guest** → Lucy + WA **askerNotice** to asker.

**Verdict: documented lifecycle exception (not silent unclassified).**

| Rule | Spec |
|------|------|
| Classification | **O11 = Invite-lifecycle continuation**, not a new free-form P-Out from current-turn model `messages` |
| Preconditions | Server-held pending **message** invite for this guest/phone; `payload == null`; single consume |
| Not allowed | Inventing new recipients/bodies from this turn’s model ACTION; collab payload invites (those use S8 / Wave 1) |
| Upstream | Creating that check/message invite / expects_reply job remains under **P-Out Gate/V** when asker originated it |
| Hardening in M1–M3 | Keep path callable only from successful register + valid invite claim; deliver asker/guest WA via **DeliveryAttempt** idempotency; no second continue after consume |
| If invite missing/wrong | No-op (already) |
| Out of Wave 1 product expansion | Cold check-with product polish stays deferred; this is **security classification**, not feature grow |

**Not an exemption from “all cross-user effects classified.”** It is classified as lifecycle continuation with the constraints above — **not** “leave for later.”

## 6. Explicit Join ≠ Share consent

Join → Member capability only. **Not** Share/Assign/Send.  
Combine only if both intents clearly presented and both covered by explicit Class V (combined or sequential). ConsentStage ≠ action consent.

## 7. Pending lifecycle UX (multi + natural)

- Many pendings, distinct ids/commands; no “כן = latest.”  
- Cancel/expire/supersede/old tap → no effect.  
- No re-confirm of side effects **inside** an already approved snapshot (including secondary notifies).  
- One confirm ≠ future blanket auth.  
- Personal ordinary ops ungated.  
- Partial/unknown → §4; remainder needs **new** confirm.

## 10. Final decisions & boundaries

### 10.1 Locked decisions

1. Gate before CORE side effects for model high-risk ACTION.  
2. Allow only Class **V** with **provenance** §2 (server command + offered proof).  
3. PendingConfirm security: bind, one-shot, TTL, cancel, execute re-check, immutable snapshot, summary≡snapshot.  
4. No outbox assumption — add **DeliveryAttempt** durable ledger; never auto-retry `unknown`/`accepted`.  
5. Failure taxonomy §4 + user-honest reporting.  
6. Join ≠ Share; full path map §5; **O11 = constrained lifecycle exception**.  
7. Natural UX: no double-confirm inside snapshot; no standing auth; personal ops free.  
8. CORE/ACTION unchanged.

### 10.2 In / out of scope

**In:** M1 ACL tests; Gate; PendingConfirm+V provenance; DeliveryAttempt; P-Out/Share/Mass; O11 constraints; legacy fire suppress; side-effect tests.  

**Out:** Class C allow; confirm-all personal mutates; P-SharedSingle; R4; CORE redesign; fire-time LLM reinterpret; Usage/Billing; Wave 1 feature expansion.

### 10.3 Certainty / V / residual

| Certain | Needs V | Residual |
|---------|---------|----------|
| No ungated model send/share-create/mass-delete/job-outbound | Completing those via offered confirm | Single-id ACL-visible mutate under PI |
| No consumable command before offer | Join+Share only if dual V | Soft LLM buttons until rebound |
| No auto resend on `unknown` | Explicit re-confirm remainder | Pre-existing reminder-fire duplicate window until DeliveryAttempt applied there too |
| O11 classified + consume-once | Asker-side invite create still V | Site UI notifies (auth session, not PI) |
